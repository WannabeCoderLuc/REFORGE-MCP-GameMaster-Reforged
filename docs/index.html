Mods built without a human in the loop.

reforge-mcp is a research and Workbench-automation server for Enfusion, built entirely from your own installation. Its purpose is that an AI can do everything — research the engine, write the files, drive the editor, compile, load and run — and build a working Arma Reforger mod with no human input at any step.

Work in progress, in the open, and measured by what it cannot yet do unattended. The server reads the game, drives Workbench and writes carefully — a custom Game Master action built through it has been watched running in a live session, and a whole cooperative scenario mod has since been authored through it and compiles clean. The remaining points where a person must still intervene are listed below as defects, not as caveats.

Introduction

What this is, and why the tooling leads.

Project Sandtable is one thing: reforge-mcp. It is a server that lets an AI ask precise questions about Arma Reforger’s engine and drive the Workbench editor directly — and the point of it is autonomy. Not an assistant that helps a modder work faster, but a server complete enough that the AI does the whole job: reads the engine, writes the scripts and configs, drives the editor, compiles, loads a world, runs it, reads the log, and fixes what broke.

That is the bar the page is written against. Anywhere a person still has to step in, the server is incomplete — and those places are named here rather than smoothed over. Building any Reforger mod counts; Game Master, Reforger’s live scenario editor, is used as the hardest worked example, because tooling that can reach into a running, network-replicated editor can reach most other things too.

This is measured by attempt, not by inventory. Building one small Game Master feature through the tooling — a context action that reports how far each selected entity floats above the terrain — surfaced seven separate defects in the tooling meant to make it easy. Every one compiled cleanly and failed silently: a base-class check that rejected the only base real context actions use, generated code with method signatures that could not compile, a config file with no GUID so the engine never registered it, and an action the engine loaded, merged, evaluated and then hid because one method was missing. Trying to build something found all of that. Counting features would have found none of it.

So the question is not how many tools exist. It is: can an AI build a real mod with this, unattended? Every friction point met while trying counts as a defect in the server — including every point where the answer was “a human does that part”.

You cannot extend an engine you cannot inspect

Reforger’s shipped API documentation is two engine versions behind, cannot be regenerated on current Tools builds, and gets some core editor inheritance backwards — one class is documented as inheriting from its own subclass. Building a deep framework on that is guesswork with extra steps.

So the instrument gets built before the thing it measures

Every index the server answers from is generated from your installation and stamped with the build it came from, so a reply can say “current”, “stale” or “unverified” instead of guessing. That is the difference between a fact about the game you have and a fact about some other version of it.

Real mods are the proving ground

Nearly every capability the server has — GUID resolution, override detection, live editor mutation with undo — exists because an actual build attempt demanded it and the naive version turned out to be wrong. Features nobody tried to use were the ones that shipped broken.

Which is also why the server is useful to a person, not only to an AI. It carries no framework and assumes no particular mod; it answers questions about Enfusion. Any Reforger modder facing the same stale-docs problem can adopt it on its own terms.

The mission

The AI does everything. That is the whole point.

The measure is not how many tools exist. It is whether an AI can be handed “build this mod” and finish it: research the engine, author the scripts and configs, register the resources, compile, load a world, run it, read the log, and fix what broke — without a human touching a file, a menu, or a dialog. Every friction point on that path is counted as a defect in the server, and every point where a person is still required is counted as an unfinished part of the job.

Hence the name. A sand table is the terrain model commanders gather around to plan and rehearse an operation — rearranged in the open, by several hands, while the situation is still moving. Game Master is that table, and it is the hardest thing in Reforger to point tooling at, which is why it is the worked example the server is pushed through.

Three places still need a person, and they are stated as gaps rather than as design. One: launching the game goes through Steam’s own confirmation prompt for custom arguments — a deliberate security control that is not the server’s to bypass, so the honest status is “blocked by design, and still a gap”. Two: four known Workbench dialogs are answered only because the owner listed them explicitly; anything unlisted is refused rather than guessed at, so a new dialog stops the run. Three: whether what happens on screen in Play mode actually reads well to a player is a human judgement, and nothing in the server attempts it.

Preserve vanilla

Anything built through the server is additive. Vanilla panels, actions and content stay — a tool that has to break the game to change it has failed, and an unattended run is exactly when nobody is watching for that.

Refuse rather than guess

Content-only config merges and scripted registration points, validated against the contract before anything is written. An unattended writer that produces something plausible-but-wrong is worse than one that stops and says why.

Multiplayer-first

Game Master is a live networked session, so generated code has to respect it: mutations validate on the server, visual ghosts never enter an RPC.

One deliverable, one bar

One server. The bar is an unattended build.

There used to be two deliverables here. Since D-0017 there is one: reforge-mcp. The Game Master framework rebuild is cancelled as a product. What replaces it as the measure is not another product but a standard: an AI, given a mod to build, finishes it without human input. Game Master is the hardest worked example to hold that standard against, not the thing being shipped. The server is intended for open-source handoff and can be adopted entirely on its own, by anyone modding Reforger.

What works today

Reads the game. Drives the editor. Writes, carefully.

Every index below is generated from your own Arma Reforger install and stamped with the build it came from — so an answer can say “current”, “stale”, or “unverified”, and never guess. Rebuilds are incremental: under a second once warm.

Beyond the indexes: the live bridge into Workbench is up, the full write set has been exercised against a loaded world of 173,637 entities, a custom Game Master action built through this tooling has been watched running inside a live session, and a complete cooperative scenario mod has been authored through the server and compiles with zero script errors. Workbench can be launched on a chosen project, made to load a world, switched between Edit and Play, and closed again — all driven from outside. One human click still breaks the chain: Steam’s own confirmation prompt for launching with custom arguments. It is a security control guarding exactly this capability and not the server’s to defeat — but against the goal of an unattended build it is a gap, and it is counted as one rather than explained away.

type-usage edges

“What does this class really inherit?”

Read from the shipped code, not a documentation dump — which had some core editor classes inheriting from their own subclasses.

“Show me one method, not a 79 KB file.”

Symbol-level slicing, and grep that reaches inside the game’s .pak archives where ordinary tools cannot look.

“Who else overrides this file?”

Mods extend Reforger by claiming the same GUID as a vanilla file. An override you didn’t know about is how Game Master mods break each other.

“What components does this prefab actually have?”

Prefabs are partial diffs over their parent, so the file alone tells you little. The inheritance chain is walked and each component’s origin reported.

Found in passing, by tooling built for something else: a stray empty override of the vanilla Game Master mode prefab, sitting inside a working mod in a folder named “trash”. Overrides bind by GUID, not by path — renaming the folder had never unbound it.

What’s new

Build log.

Dated, specific, and honest about what broke. Entries are written when the work lands, not when it is planned — every claim here is traceable to the project’s evidence ledger.

  1. 9 Sep 2026 Fixed

    Running the workflows for real found what dry-running them could not

    The rewritten configs were applied to a live addon, registered through the editor, and loaded. Two results. The config fix is confirmed: the engine parsed past the container and reached the entries, where the old template would have died at the root on a class that does not exist. And a new defect surfaced that no dry run could have shown — pointed at a plain subdirectory rather than an addon, every tool wrote its files happily, the .conf registered and was assigned a GUID, and the engine then reported Unknown class, because Enfusion compiles scripts under an addon's own Scripts/ directory and nowhere else. Not a compile error. No compilation at all.

    The target folder is now checked for an addon.gproj before anything is planned. Separately, wb_inspect turned out to have every part except the line that ships it: handler, implementation and import all present, documented in two files, and missing from the registration table — so it was documented, implemented, and absent. That is 72 tools now, not 71.

    Both defects have the same shape as the ones before them: the work succeeded at every step that reports, and failed at the one that does not.

  2. 9 Sep 2026 Fixed

    The framework workflows were writing configs the engine cannot read

    The six framework workflows check the base class of every script they generate — that guard exists because getting it wrong is the classic silent failure. Nothing checked the class names they wrote into the configs. Auditing all six against the installed build found six classes that do not exist: three invented outright (SCR_EditorActionsConfig, SCR_EditorAttributeCategoryList, SCR_PlaceableEntityItem) and three belonging to the framework that was cancelled before it was built.

    So five of the six emitted at least one file that parses, loads and registers nothing. The real shapes, read back out of the shipped configs, were different in kind rather than in detail: an action list is SCR_EditorActionList with per-entry GUID tokens and an m_Info block, not an id-and-name pair; an attribute category is its own resource file referenced by GUID, not a string naming a tab; and the placeable registry exposes a directory rather than holding a list of items.

    All three are rewritten against the shipped configs, and the systemic hole is closed: every class name a workflow is about to write is now verified against your build first, and an unbuilt index says so rather than reporting correct classes as missing. Twelve new tests across the two trees.

    One test had been asserting the bug. It checked the generated action list contained m_aActions +{ and passed for as long as that was what the template emitted — a test written against the template rather than against the engine confirms whatever the template does, including nothing.

  3. 9 Sep 2026 Changed

    The bridge handlers carry the project’s own name now

    The 23 handler classes inside Workbench were still named for the third-party server this project started from. They are now SANDTABLE_WB_*, in a Scripts/WorkbenchGame/Sandtable/ folder, across both the private and open-source copies. This is not cosmetic: the class name is the wire protocol — a request names the class it wants — so the rename had to land atomically in the handlers, the server that calls them, the safety allowlists and the tests, or the bridge would answer nothing.

    Handler lint is clean on all 23 files in both trees, and both suites are green — 372 tests private, 353 plus 3 intentional skips open source.

    Verified in a live editor, not inferred: Workbench was launched on the handler addon, the log confirms the addon loaded, the script module compiled with zero errors, and requests addressed to the new names came back — including action-dispatched handlers, whose read-action allowlists key on the very class name that changed.

  4. 9 Sep 2026 Fixed

    A mangled path started the server anyway

    Repairing the config produced a better bug than the one being fixed. Written through a shell that stripped backslashes, every path arrived as C:Program Files… — which Windows accepts, because it means “relative to the current directory on drive C:”. Nothing threw. The server started, announced all 71 tools, and every configured root silently resolved somewhere else. The only symptom was diagnose marking each path MISSING, which reads like a broken install rather than a mangled string.

    That is precisely the failure an unattended run cannot notice, so it is now refused at startup with the cause named rather than reported later as five unrelated missing directories. Absent-but-well-formed paths still only warn — a missing Tools install leaves the research profile perfectly usable, and refusing to start would be the worse answer. Six committed regression tests in each tree, plus an end-to-end check that mangles the real config and confirms the server now refuses it.

    The wider lesson, and the reason it is written down: the bug was never in the path logic. It was that a wrong value looked exactly like a right one to everything downstream.

  5. 9 Sep 2026 Fixed

    The config had been quietly pointing at deleted folders

    A workspace reorganisation removed the old project tree and two addons. Nothing announced it. What was left behind: two of three configured roots pointed at folders that no longer existed, the docs path pointed into a deleted tree, the declared profile contradicted the one actually launched, the handler addon still declared a dependency on a deleted addon’s GUID, and the resource index still answered with paths inside it — so a same-GUID override check could be “verified” against a file that was gone.

    All of it is repaired and re-indexed from the installed build. Two tests that had been asserting on the deleted addon were rewritten to assert on the code rather than on the owner’s config — one of them had been demanding that some framework root exist, which made a passing test a statement about a folder instead of about the server.

    Worth naming as the pattern: none of this failed loudly. It sat as stale truth in a config file, which is exactly the failure mode an unattended run cannot notice.

  6. 9 Sep 2026 New

    A whole mod, built through the server

    The question this project now exists to answer — can a real mod be built with this? — has its first substantial answer. A cooperative scenario mod was authored end to end through the tooling: replicated component state with server-authoritative transitions, a continuous repair interaction with distance and interruption handling, a coverage evaluation over relay positions, three authored incidents, a Game Master action for inspecting and toggling a relay, and its own documentation set.

    It compiles clean — zero script errors across all four modules, checked headlessly in seconds rather than by restarting the editor. Three defects surfaced on the way and every one was fixed from log evidence rather than guesswork: a component that could not be allocated the way the code assumed, a class-binding mismatch the engine reported plainly once anyone read the log, and a same-GUID override that had to be renamed to match its target’s exact path, because Enfusion matches overrides by path as well as by GUID.

    Still unproven, and stated as such: everything that can only be seen in Play mode. The scripts load and the logic compiles; whether the on-screen prompts read well to a player is a human’s judgement and has not been made yet.

  7. 9 Sep 2026 Fixed

    Entity names came back as raw localization keys

    The ground-check action reported entities by an identifier like #AR-Role_CC rather than a readable name — cosmetic, but it degraded the exact diagnostic the action exists to produce. The name now goes through the engine’s own translation call before it is printed.

  8. 9 Sep 2026 Changed

    The goal changed: the server is the project now

    Rebuilding Game Master as a framework is cancelled. The whole project is the server, and Game Master is kept as the thing the server has to be able to mod — the benchmark, not the product. The fourteen wanted features are now a bank of test cases; each one is something to attempt through the tooling, and whatever gets in the way is logged as a defect in the tooling.

    That was decided on evidence rather than preference. Building one small Game Master feature — a context action reporting how far each selected entity floats above the terrain — surfaced seven defects in the scaffolding meant to make exactly that easy. Every one of them compiled cleanly and failed silently: overrides written with the wrong number of parameters, a generated config with no sidecar and therefore no GUID, folders emitted in the wrong place, and a base-class check that compared names instead of asking what a class actually inherits from.

    Trying to build something found all seven. Counting features would have found none — which is the argument for the change, and the reason the feature list is kept rather than deleted.

  9. 9 Sep 2026 New

    Workbench opens, loads a world, switches mode, and closes — on command

    Five capabilities were named as the definition of “usable”, and all five now have a reading behind them rather than a call that returned success. Workbench launches on a chosen project — proven by the session log listing all five project files as loaded addons, not by the process appearing. It closes and restarts cleanly. It creates addons and loads worlds both at launch and mid-session — proven by the live entity count going from 1 to 173,637. It switches between Edit and Play in both directions, with the mode re-read after each switch. And it searches Bohemia’s own published API documentation through two new tools.

    Two of those took a correction first. Launching by running the executable directly dies on “Could not initialize Steam platform”, because it is a Steam build — the launch has to go through Steam itself. And loading a world failed until it became clear the call had been aimed at the wrong editor module all along; the module you ask decides which editor opens the file.

    One human click remains and stays: Steam’s own prompt confirming a launch with custom arguments. It guards precisely this capability, so it is documented rather than defeated.

  10. 9 Sep 2026 Fixed

    Ten more double-length lists, and a rule that could not be checked

    The bug that made every list from the bridge come back at double length was fixed once and found again in ten more places across eight handler files — the same mistake in a second shape nobody had looked for. All ten are corrected, and the check that catches them is now a linter with seventeen committed regression tests behind it.

    It needed them. The previous guarantee pointed at a backup folder on one machine that has since been deleted, which quietly made the claim unfalsifiable. Writing the tests also caught the linter’s own headline rule failing on its headline case: a loop declaring two variables at once, the exact construct Enforce rejects, was slipping past because the rule was anchored to the start of a line.

  11. 9 Sep 2026 New

    We closed the build gap with the official API

    We ingested more than 33,000 files from Bohemia Interactive’s official Doxygen output and found the interfaces our project had been missing: the supported Workbench CLI for headless validation, cooking and packing, plus built-in Net API calls including ValidateScripts, IsWorkbenchRunning and ReloadScripts. Those calls surface structured compiler errors without depending on a custom handler. The same pass exposed EvaluateScript; we treat that arbitrary-execution surface as untrusted and keep it locked down.

    That evidence turned mod_build from a documented omission into a shipping tool. It now validates scripts headlessly with -wbSilent, builds target-platform data with -run -builddata, and packs cooked addon directories with -packAddon. Publishing and login flags are rejected, only one build may run at a time, and the result is checked against the logs rather than trusting a zero exit code.

    Verified live: engine registration succeeded, and mod_build validate has since compiled all four script modules headlessly in about five seconds — a gate cheap enough to run after every handler edit instead of paying for a restart. build and pack are implemented but have not yet been run. We also confirmed that Workbench plugin APIs are limited to World Editor and Script Editor.

  12. 8 Sep 2026 New

    Scale and Stability: 13 MCP Features, Subagents, and Bridge Fixes

    Identified and fixed Enforce script syntax errors (comma initialization and ternary operators) in EMCP_WB_Inspect.c that caused Workbench crashes. Created 5 new SKILL.md files (mcp-gamemaster-site-workflow, workbench-safety-model, mcp-server-dev, game-master-framework-dev, enforce-script-gotchas) to encode project constraints. Defined 3 new Antigravity subagents (researcher-planner, programmer-tester, api-handler-creator) and established a new roadmap of 13 MCP programmatic features and 3 specialized AI agents.

  13. 7 Sep 2026 New

    Same-GUID overrides union — so extensions can be separate addons

    When two mods claim the same file, does the engine keep both contributions or only the last one? It keeps both. A second mod — written to know nothing about the first, and deliberately loaded after it, the order that would have made the first disappear — was added, and the editor came back carrying both. Eighteen pieces without it, nineteen with, the difference being exactly the newcomer.

    Two earlier explanations for why this wouldn’t run were mine, and both were wrong: first the two mods conflicting, then a corrupted profile. The actual cause came from watching someone use the editor — the session spawns wherever the camera is, so pressing play with the camera nowhere useful has nothing to spawn into. Neither wrong guess was ever written down as a finding, which is the only reason the record is still worth reading.

  14. 7 Sep 2026 New

    One API instead of one handler per question

    Asked why the tooling couldn’t be general rather than Game-Master-specific, the answer turned out to be that it can. The engine exposes enough reflection for a single routine to describe an object whose type the code has never seen — so “what is attached to the editor right now” became one call instead of a new handler, a restart, and a log scrape.

    Building it found a bug in the handler it was modelled on: every list the bridge returned had been coming back at double length, padded with blanks, for weeks. Nobody noticed because callers read the count rather than the list — and that same bug had quietly disarmed a safety check in the undo path.

  15. 7 Sep 2026 New

    The gate experiment passed

    One experiment blocks all the others: does adding the framework to Game Master’s edit mode quietly break vanilla? It now has a dated answer on a real build — the editor’s own component census comes back complete with the framework’s piece added, not substituted, and a human confirmed the browser, command bars, properties, layers and budgets are all still there.

    The runner that produced it has one rule worth stating: a check it cannot see is reported unobserved, never passed. Five of the eight are things only a person can judge, so the overall verdict stays inconclusive even though the experiment’s own acceptance criterion is met — and the report says both, because collapsing them would hide that the gate is clear. Human answers are stamped with the build they were made against, and expire when it changes.

  16. 7 Sep 2026 Changed

    A rename switched two safety rules off, silently

    Renaming a folder disabled a write guard that was keyed on the old name, and a second rule that kept 55 MB of licensed art out of a public repository. Both had been correct for months and neither announced that it had stopped applying.

    The test that should have caught the first kept passing, because it asserted on the old name appearing in some output — and an unrelated hard-coded string still contained it. Rules now ask the thing itself rather than its label, and a boundary test that had been passing vacuously was found in the same sweep.

  17. 7 Sep 2026 Changed

    One workspace became four projects

    Two axes — server or editor, open source or personal — crossed into four. The second axis is the one that does the work: the moment a licensed UI pack enters a build, that build can’t be the open-source one. So the line is drawn by which folder the assets live in, rather than by remembering the rule at publish time.

    The dependency direction was inverted at the same time. The tooling addon may depend on the mod; the mod must never depend on the tooling. It had been the other way round, which quietly wired the debugger into the shippable thing and made “strip it before publishing” a human’s job.

  18. 7 Sep 2026 New

    Fourteen wanted features, and one was already finished

    A wishlist arrived: patrol areas, trigger zones, garrisons, saveable compositions, undo, session save. Reading it against the code, the last item — letting other mods register their own commands — turned out to be the piece already built and proven. It isn’t the fourteenth feature; it’s the spine the other thirteen hang from.

    Which promotes one unanswered question to blocking. When two mods override the same file, does the engine merge them or keep only the last? If it’s the latter, “features are addons” collapses and the design changes. That gets answered before anything is built on top of it.

    First attempt: inconclusive, and logged as such. The second override compiles clean and loads, but the session that would have answered it ended in the editor falling back to a menu — which is consistent with the overrides conflicting and with an unrelated fault, because the control run never completed. One result short of an answer is not an answer.

  19. 7 Sep 2026 New

    Dialogs can be answered, not only declined

    The unattended dialog sweeper is reject-only by construction — that’s what made it safe to leave running. But some prompts need a real answer, so a second mechanism now sends one: a specific named button, for a specific named dialog, only where the owner has opted that dialog in.

    There is deliberately no “press the default button” shortcut: on the engine’s assertion box the default is Abort, which kills the editor, while the wanted answer is Ignore. Status: implemented and policy-verified, but not yet observed answering a real dialog — two attempts to demonstrate it failed for reasons of method rather than defect, and it’s logged as open until one is caught in the act.

  20. 7 Sep 2026 Fixed

    A capability we’d written off was there all along

    Setting the editor’s selection from outside was recorded as impossible — on the strength of a comment inside the bridge code saying the engine didn’t offer it. The engine offered it two lines away in the same interface that code was already using.

    Rewritten, it worked on the first attempt. The rule that came out of it: a comment is not evidence, and neither is an absent feature until the declaring class has been checked.

  21. 7 Sep 2026 Fixed

    Copy-paste could corrupt a world, and its undo never worked

    Pasting a duplicate of a one-per-world entity made the engine assert. And the undo built for pasting — comparing entity names before and after — could never have worked, because pasted entities routinely have no name at all.

    Pasting now requires explicit confirmation and warns about duplicating singletons, and the undo defers to the editor’s own undo stack, which handled the case our approach couldn’t even see.

  22. 7 Sep 2026 New

    Workbench runs unattended

    A modal dialog blocks Workbench’s event loop — the same loop that answers the automation bridge — so while one is open, nothing inside the editor can clear it. The server now detects and dismisses those dialogs from outside the process, and can start, close and restart the editor itself.

    Dismissal is reject-only: it can decline a prompt but never accept one, so it cannot confirm a destructive action on your behalf. Save, overwrite and delete prompts are permanently excluded and always left for a human.

  23. 7 Sep 2026 Fixed

    Copying a world silently corrupted it

    Enfusion worlds are binary. The duplicate tool read them as text, so an 867-byte world came back as 950 bytes of replacement characters — unopenable, with no error reported. Copies are now byte-exact.

    The same fix caught a second half of the bug: the sidecar file named a resource class the engine does not have. Class names are now taken from a verified table, and an unknown file type is refused rather than guessed.

  24. 7 Sep 2026 Fixed

    Two tools reported success for nothing

    Running the write tools against a real 173,637-entity world found one that reported a tick — and recorded an undo step — for an operation the engine cannot actually perform, and another that would have coerced a mistyped layer name into layer zero, locking the entire world.

    Both are now impossible: a handler answering “ok” while doing nothing is treated as a failure, and layer ids are validated against the layers that exist. Neither would have been caught by a test fixture.

  25. 7 Sep 2026 Changed

    A timeout no longer means “it didn’t happen”

    A call timed out while the operation it requested had in fact completed — so a real change went unrecorded, and a retry would have applied it twice. Timeouts now report an explicitly unknown outcome and say to verify before retrying.

  26. 7 Sep 2026 New

    The write surface is complete

    Every writer the specification lists now exists: live entity, component, clipboard, layer, prefab, resource, script and localization editing, plus session control — and five scaffolders that consult the indexes before emitting anything, so generated code matches the build you actually have installed.

    One is deliberately absent. Packaging has no engine handler, so rather than fake it through the bridge, it stays unbuilt and visibly listed as such.

  27. 7 Sep 2026 New

    The live bridge came up

    The editor connection that had blocked this project since its second session now answers. The cause of the last hang was ours: the client wrote its request without closing the socket, and the editor reads until end-of-input — indistinguishable, at the network level, from a missing handler.

  28. 6 Sep 2026 New

    Indexes built from your own install

    Symbols, resource GUIDs and a full class hierarchy, all derived locally and stamped with the game build they came from. The shipped documentation index had core editor classes inheriting from their own subclasses; the source-derived one replaced it.

Many of the entries above are defects found by running the tools against a real editor rather than a test fixture. They are listed because a build log that only records wins is not a build log.

Knowledge

Shipping

Derived indexes built from your own installation. No Bohemia content is redistributed — every index is generated locally and stamped with the game build it came from.

  • symbol_lookup a class or enum's real declaration, inheritance chain, members, methods and usedBy
  • signature_check verify a method exists with the signature that actually shipped
  • prefab_resolve a prefab's merged component set, with each component's origin
  • guid_resolve · path_guid resolve a resource GUID either way, reporting how it was determined
  • resource_refs who overrides, inherits from, or references a resource
  • config_merge_preview preview a same-GUID override before it silently replaces vanilla content
  • addon_deps read .gproj manifests and the addon dependency graph
  • api_search · component_search the documentation index — superseded by symbol_lookup, kept as a fallback
  • wiki_search · wiki_read · kb_search indexed BI wiki and a distilled modding knowledge base

T2 · T4

Write & mutate

Shipping · opt-in

Every writer runs behind a twelve-point safety model: writes confined to declared mod roots, dry run by default with a single-use plan id, an operation journal that records how to reverse each change, explicit confirmation for anything irreversible, and no publish tool at all.

  • file_write write into a writable mod root — returns a real diff first, changes nothing until applied
  • intervention_undo replay recorded inverses, newest first
  • mod_scaffold · game_duplicate a new addon skeleton, or a vanilla resource copied with a fresh GUID — a copy that keeps the original GUID is a merge, not a duplicate
  • script_scaffold subclass a base class using the overridable signatures that shipped in your build, read from the symbol index
  • config_scaffold · layout_scaffold new .conf / .layout resources with minted, collision-checked GUIDs and their .meta
  • wb_entity_create · wb_entity_modify · wb_entity_select spawn, edit and select live entities; undo restores the prior state, selection included
  • wb_entity_delete needs explicit confirmation, and is honest that undo will not bring it back
  • wb_component_edit · wb_clipboard_op · wb_layers_edit the live editing surface — a paste is undone through the editor’s own undo stack, because pasted entities frequently have no name to delete them by
  • wb_script_edit line edits with a Reload Scripts step attached, because entering play mode does not recompile
  • wb_prefab_save · wb_resources_register · wb_localization_edit write entities out to prefabs, give new files their GUID, edit the string table
  • wb_save · wb_open_resource · wb_play / wb_stop drive the editor session itself — including loading a world into the running editor, which needs the world target specifically, because the module you ask decides which editor opens the file. Opening a resource is transition-guarded, because doing it mid-transition has crashed Workbench
  • wb_menu_action allowlisted menu actions only — an allowlist, never a blocklist
  • wb_dialogs clear the modal dialogs that block the editor's automation bridge — reject-only, so it can decline a prompt but never accept one
  • wb_process start, close and restart the editor; handler code only registers at process start, so this is what makes an unattended add-and-verify loop possible
  • exp_run drive a validation experiment and emit a structured report — a check it cannot observe is reported unobserved, never passed

Reversibility is decided per operation, not claimed per tool. Some undo exactly (a layer lock is a toggle; a script line edit restores the prior text). Some are derived (a paste is undone by diffing the entity list before and after). The rest — saving a prefab, registering a resource, deleting a row — record no inverse and say so, because a fabricated undo that looks like a restore is worse than none.

Next

Framework workflows

Shipping · opt-in

The extension contract turned into guided automation. These are not file writers: each validates the contract before writing and refuses with a pointer to the clause, because every rule below guards a mistake that compiles cleanly and then misbehaves somewhere else.

Since 9 September that validation covers both halves of the output — the base class of the generated script and every class name written into the generated configs, each checked against your installed build. It did not always: an audit that day found six config classes that do not exist, and five of the six workflows were emitting at least one file that loaded and registered nothing.

  • framework_addon_new a scripted extension addon: manifest class the registrar can find, plus the folder layout the contract expects
  • framework_action_add a command action, its registry merge, and the keybinding entry that makes it rebindable — an un-namespaced id is refused, because registry ids are shared and a bare word collides with whoever else picked it
  • framework_attribute_add an Edit-Properties attribute plus the category tab it needs — an attribute in a tab that does not exist simply never appears
  • framework_panel_add the component + layout pair, with an explicit Z band. Not optional: vanilla reserves the top of the range and widget order is otherwise decided by insertion, so a panel without one is positioned by accident
  • framework_placeable_add the editable wrapper that makes a prefab placeable, with a fresh GUID — a wrapper reusing the source's GUID would override it instead
  • framework_mode_override_apply the single minimal-diff mode override, GUID re-verified against your installed build first — an override pinned to a GUID that moved loads, compiles, and silently overrides nothing
Build

Headless validation, build & pack

Shipping · guarded

Official Workbench CLI documentation replaced the earlier assumption that packaging had no safe automation path. The build process remains separate from the live editor bridge and is constrained to three enumerated actions.

  • mod_build validate headless script compile check through -wbSilent, with structured errors surfaced from Workbench
  • mod_build build compile mod data for an explicitly selected target platform through -run -builddata
  • mod_build pack archive an existing cooked addon directory through -packAddon

The final argument vector is checked for publishing and login parameters, concurrent builds are refused, and logs are scanned after execution. A zero exit code by itself is never reported as proof of success. EvaluateScript remains unavailable.

Two rules hold across every tier: results say which game build they came from, so a stale answer announces itself; and nothing that reaches outward — no Workshop upload, no publish — exists as a tool at all.

The bridge

Handlers: the editor’s side of the conversation.

The most-asked question about this project is how a program outside Arma Reforger can drive the editor inside it. The answer is a small addon of handlers, and understanding them explains most of the server’s design.

What they are

Workbench ships a network listener but no functions. It accepts a request naming an operation and looks for a script class that implements it — and if none exists, nothing happens. A handler is that class: a small piece of the editor’s own scripting language saying “when this request arrives, run this inside the editor, and send this back”.

23 of them, in a dedicated addon. They are the bridge’s entire vocabulary.

Why they’re necessary

Everything the editor knows — the entity list, resolved prefab components, the resource database, the selection, the undo stack — is reachable only from inside the editor’s own script environment. There is no outside interface to any of it.

So if the handlers don’t expose a capability, it doesn’t exist for the server. No amount of work on the outside creates it. Adding a handler is a normal step, not an exotic one.

Why they’re a separate addon

They are development tooling, not game content. Keeping them apart means the mod being worked on stays clean, and retires an old hazard from the predecessor tool: it injected handlers into whichever project was open, so merely connecting modified the thing under test.

They used to be stripped from the mod’s dependencies before a release — until it became clear that a rule requiring someone to remember something is not a rule. The direction is now inverted: the tooling addon may depend on the mod, never the reverse, so the mod ships correct without anyone doing anything.

What they cost

A handler only becomes live when the editor restarts. Reloading scripts does not update handler code at all — not new classes, and not edits to existing ones either, which was assumed to work until it was tested. And an edit is all-or-nothing: one bad symbol fails the whole script module and takes every handler offline at once, not just the edited one.

That happened here. A method that exists — but on a different class than assumed — took the bridge down until the file was reverted.

A comment inside a handler is not evidence either. One claimed the editor could not set a selection programmatically, and its code did nothing while still reporting success. The engine had offered that call all along, two lines apart in the same API the handler was already using — rewriting it made selection work on the first try.

The general API

One API, not one handler per question.

Every capability the bridge had arrived as its own handler, so “let me look at X” meant writing and compiling something for X. Asked why this couldn’t be general instead, the honest answer turned out to be: it can — and the engine had the mechanism all along.

What made it possible

Enforce exposes real reflection. Any object can be asked for its own type, and any type can be asked to enumerate its variables — names, types, and values. So a single routine can describe an object of a type the code has never heard of.

That is the difference between a hundred handlers and one.

The question it finally answers

Whether the Game Master editor is actually open, and what is attached to it. That sounds trivial and wasn’t: the tooling could see the world editor’s mode, but a session can be running with Game Master closed — a different question, and the one that mattered.

The old workaround was to instrument a component so it printed its own state, then read the log. Which works only where you already put the component.

Where it stops

There is no way to look up a type from a piece of text at runtime, and no way to execute code. So it inspects any object it can reach — never an arbitrary type by name. Reachability is the only part fixed at build time, and widening it is a one-line change.

Stated here rather than discovered later by someone expecting otherwise.

What building it exposed

Writing a second handler of a kind is how you find out what was wrong with the first. Every list the bridge returned had been arriving at double length, padded with empty entries — for weeks, unnoticed, because callers read the count rather than the list.

And that bug had quietly disarmed a safety check in the undo path, two layers away, invisible from either end alone.

Verified against a live session: the editor reported itself open, named its mode, listed all nineteen components attached to it, and returned real values off the manager’s fifty-three fields — answering in one call what had previously taken a restart, a manual step, and a log scrape.

Architecture

Four seams the tooling has to work through.

These were the pillars of the cancelled framework. They are kept because they are the real structure of the problem: any tool that means to change Game Master has to go through these four seams, so they are what the server is exercised against. Each one is a verified Enfusion seam, not a proposal.

  1. 01

    Extend native components

    Precision transform, deep attributes, and advanced logic/waypoints by subclassing SCR_TransformingEditorComponent, SCR_AttributesManagerEditorComponent, and SCR_CommandActionsEditorComponent — not replacing the editor.

  2. 02

    Non-destructive mode override

    A minimal same-GUID override of EditorModeEdit.et injects custom components and UI panels while third parties register through framework-owned lists.

  3. 03

    State serialization pipeline

    Walk editable entities, record transforms and AI order state, reload via server-authoritative SpawnEntityResource — portable scenarios, not fragile SaveGame snapshots.

  4. 04

    Authority separation

    Client UI visualisation vs server execution. Pattern: client request → server re-validate → perform → owner callback. Ghosts and outlines never leave the client.

Pillar 02 is no longer a plan. The minimal override is written, it attaches the framework to Game Master’s edit mode, and it has been confirmed running inside a live vanilla world — 0 script errors, 1 component added, 115 untouched. The component count came back two short of expectation and reconciled to two vanilla components that ship switched off, which is the sort of thing worth checking rather than rounding away.

Why it matters

Three things nobody has done live in Arma.

These are not promises and not shipped features — nothing is being built to deliver them. They are here as the hardest things anyone could hand an AI and say “build this”: each is rated hard in the feasibility notes and sits at the top of the community’s complaints. That combination makes them the most useful place to find out where the server stops being enough on its own.

Concurrent multi-GM editing

Real permission + concurrency model. Vanilla IsAdmin() is a stub; 3DEN is single-user offline.

Multi-step undo / redo

No prior art in Arma live sessions. Vanilla rewind is a single SaveGame snapshot, not a command stack.

Live triggers & conditions

General “when X, do Y” authored while players are in the world — GM has no free trigger primitive today.

The fourteen things Game Master is actually wanted to do. Reading the list against the code produced two findings: the last item was already built, and four of the others are one feature wearing four hats.

Built already

  • Mod extension registry — letting other mods add commands, waypoints and presets. This is the spine, not the fourteenth feature.

Instrumentation first

  • AI status inspector — read-only, and the debugger for every AI feature below. Build the answer before the features that raise the question.

Proven ground

  • Patrol area — an increment on a shipped, working mod
  • Group behaviour presets — shares the property audit

One substrate, four faces

  • Linked tasks
  • Objective builder
  • Trigger zones
  • Reinforcement rules

Content authoring

  • Saveable compositions
  • Layers and collections
  • Garrison area — guard positions yes; automatic building positions is a research project, deferred on purpose

Handle with care

  • Undo / redo — the editor already has an undo stack, and two stacks over one world is a correctness problem, not a feature
  • Session save / restore — the only item where a bug costs work rather than merely failing

One open question gates the other thirteen. When two independent mods override the same file, does the engine merge both or keep only the last? Merge, and features can be addons and outsiders can extend them. Last-wins, and everything has to funnel through a single override — a different architecture.

Answered: they union. A second, deliberately independent override — one that knows nothing about the framework — was loaded after it, the ordering under which last-wins would have dropped the framework’s own component. The mode came back carrying both: 18 components without it, 19 with, the difference being exactly the newcomer. Nothing replaced.

Asserted three ways that don’t depend on each other: each addon censused the editor separately and both reported seeing the other, and the probe published its own one-line verdict so the answer never rested on someone counting names correctly. Features can be addons. Outsiders can extend them. Thirteen of the fourteen are unblocked.

Extension model

Two tiers. No third path.

Creators never override the mode prefab. Contribution goes through framework-owned configs and registrars — the fragile surface stays owned.

Tier A — Content-only

A .conf merge into a framework-owned list. No Enforce scripting. Placeables, presets, display categories.

Tier B — Scripted

An SCR_* subclass plus a registration call. Custom AI orders, panels, trigger conditions, permission policies.

Shipped proof: GMPW Auto Patrol — custom waypoint via same-GUID config merge, live-editable and replicated. That recipe is the template.

Using it

Install, point it at your game, ask it things.

The server is MIT-licensed and runs locally. It redistributes no game content — every index it answers from is generated from the copy of Arma Reforger you already own, and stamped with the build it came from.

1 · Install and index

Clone, npm install, npm run build. Copy the example config and set four paths: your game, your Tools install, your Steam steamapps, and your Workbench addons directory.

Then build the indexes. They take seconds, and they come from your installation rather than from anyone else's.

2 · Start in read-only

It ships in the research profile: twenty-four tools, no writers, no editor required. Everything about the engine — symbols, GUIDs, overrides, prefab resolution — is answerable in this mode with Arma Reforger closed.

Most people never need more than this.

3 · Add the bridge, if you want the editor

Editor features need a small handler addon installed into Workbench and a restart, because handler classes only register at process start. Without it the editor tools cannot connect and everything else carries on working.

The server never installs it for you — modifying your project as a side effect of connecting is a hazard, not a convenience.

4 · Only then, enable writes

The workbench profile lets an assistant edit files in the mod roots you declare and change a live editor session. That is a real decision, not a formality.

Put your mod in version control first. The safeguards below are good and have been exercised — they are not a guarantee.

Precautions worth reading before you enable writes

Everything here has actually happened during development. None of it is hypothetical.

Some things cannot be undone

Deleting an entity, saving a prefab, registering a resource and saving the world record no inverse and say so. Saving in particular commits every unsaved change at once — including ones you made by hand that the server knows nothing about.

A fabricated undo that looks like a restore is worse than none, because it is believed.

Undo does not survive a restart

The journal of how to reverse each change lives in the server process. Restart it and the changes remain on disk but can no longer be reversed. Undo soon, or not at all.

Deliberate: persisting it would imply a guarantee across restarts that nothing has verified.

Driving a live editor has crashed it

Opening a resource mid mode-transition crashed the editor natively. Pasting a duplicate of a one-per-world entity made the engine assert. Repeated forced closes hung it twice.

Do not run this against a session holding work you have not saved.

A green report is not a safe outcome

An automated run once placed a camera over open water at altitude, spawned a character into the sea, and reported success at every step — because nothing was checking where the camera had ended up.

Checks confirm the things they check. That is all they confirm.

Two guarantees hold whatever you enable. There is no publish tool — no Workshop upload, no release step, nothing outward-facing, and a test that fails if one is ever added. And the dialog dismissal used for unattended runs is reject-only by construction: it can decline a prompt but is structurally incapable of accepting one, so it cannot confirm a destructive action on your behalf.

Standing goal

Open source. Handed to the community.

The server is published. github.com/WannabeCoderLuc/reforge-mcp

MIT, 71 tools in the published build, and it stands alone — it knows nothing about any framework and answers questions about Enfusion. Clone it, point it at your own installation, build the indexes, and start in the read-only profile. No game content is redistributed: the indexes are generated locally, because they are derived from the copy of the game you own.

There is no second package coming. The framework that was going to follow it is cancelled, so the server is the handoff.

The workspace is split four ways: a server and a Game Master mod, each in a personal and an open-source edition. The open-source editions are extractions of the personal ones once those work, not a second effort running in parallel — building the same thing twice at once is how both end up half-finished, and extracting means the licence-clean edition is made by removing encumbered assets from something already proven. The two server trees are deliberately not mirrors: the public one ships no user config and omits the experiment runner, so copying files wholesale between them breaks it — and has.

  • README — what it is, install, the paths to configure, quickstart
  • API — every tool by tier, with what each actually guarantees
  • HANDLERS — the editor addon: installing, extending, and the traps that cost an afternoon
  • WARNINGS — precautions, every one of them something that actually happened
  • HIGHLIGHTS — the nine capabilities that define how it works
  • COMPATIBILITY · build tracking · migration notes
  • VALIDATION from the experiment results
  • MIT for the server · framework licence tracked separately

The split is drawn by redistribution, not secrecy — and the distinction that matters is that “personal” removes the open-source obligation, not the asset licence. A Workshop upload is redistribution whether or not the source is public. So the boundary is structural: which folder the art lives in decides which build can contain it, rather than someone remembering the rule at publish time.
